# Phase D−1 — Intake & warm-catalog-first check (REQUIRED, runs before Phase D0)

Two parts. **Part A (intake & mapping)** follows the `intake-and-mapping` skill verbatim — same codebase discovery (`$REQ_DIR/codebases.json` → frontmatter → cwd → ask user), same per-codebase ct6-converge workflow with cartographer + route-mapper + 3-reviewer convergence, same map-freshness rules, same integration mapping, same wing-scoped MemPalace wake-up + mining. The freshness pre-scan is non-negotiable; a data plan proposed against a stale map is worth as little as a bug fix proposed without a replication.

**Part B (the warm-catalog-first check — the first new discipline).** BEFORE considering a data-dictionary rebuild, query the Run A knowledge server (`services/knowledge_server/`, installed via `/architect-team:knowledge-install`) for the dictionary and its freshness verdict. Call the server's `get_dictionary_status` tool — it returns `built_at`, a `repo_side` reference-file drift verdict, a `db_side` currency arm, `reference_file_count`, and the `freshness` envelope (`{verdict: current | stale | unknowable, basis: [...]}`). Record the returned verdict into the run's inputs at `<workspace>/.architect-team/data-eng/<slug>/warm-catalog-check.json`.

This is deng's *"check the catalog, not the database"* discipline — but with a precise division of authority: **the server's freshness verdict INFORMS; the per-run gate DECIDES.** A `current` verdict is a strong signal the existing dictionary can be reused as-is (skip the rebuild, cite the warm catalog as the model of record); a `stale` verdict is a strong signal a D7 rebuild is warranted; but neither the server verdict alone decides — the D1 plan's own acceptance criteria (does THIS ask touch tables the dictionary already covers, at the grain it records?) make the final call. The server never overrides the run; it saves the run from rebuilding a catalog that is already warm.

**No-connection honesty (carried from Run A).** If the knowledge server is not installed or not reachable, degrade gracefully: record `freshness: {verdict: unknowable}` and proceed to build the dictionary from scratch at D7. And regardless of connection, the DB-currency arm is `unknowable` without a live database connection — the reference-file (repo-side) drift arm can say the code touching the dictionary's tables changed, but whether the underlying data itself drifted is **unknowable** without a live connection. State that boundary plainly in the warm-catalog-check record and in the final report; never imply the catalog is verified current against the live database when only the repo side was checked.

**Part C (the Bauplan arming check — additive; a no-op on a project that is not Bauplan-shaped).** Resolve whether this run arms the optional `bauplan` lakehouse capability, per `common-pipeline-conventions` `## Augment-never-replace discipline (v3.63.0)`. Two signals, handled asymmetrically: a `bauplan_project.yml` anywhere in the target repo — detected by `_has_bauplan_markers` in `hooks/discipline_registry.py`, recursively, so a monorepo subdirectory marker counts — is a deterministic trait and arms the path **silently**; stated Bauplan intent in the ask with no marker (the greenfield case, where no marker can yet exist) surfaces **exactly one** confirmation — owed BEFORE the first bauplan-specific dispatch, not at some later convenience — and arms only on an affirmative answer. Certain signals act; inferred signals ask. Resolve it through `resolve_bauplan_arming` in `scripts/bauplan/arming.py` — a pure function, so the decision is the same every time it is asked — and record the returned `{armed, signal, requires_confirmation, disposition}` at `<workspace>/.architect-team/data-eng/<slug>/bauplan-arming.json`. That confirmation is a **domain gate**, not process ceremony — the user's answer determines what gets built — so it fires regardless of the v0.9.20 process-gates-opt-in rule. A declined confirmation is recorded there and in the final report, and is not re-asked.

**Everything Bauplan in D0 and D2–D6 below is gated on that verdict being armed.** When it is not — the ordinary case for the overwhelming majority of runs — this lane reads **no Bauplan instruction at all** and every phase proceeds exactly as it does today. When it IS armed and the `bauplan` plugin turns out to be absent, warn and degrade per the canonical section: run the generic path, and name the missed capability plus its remediation in the final report rather than proceeding silently. Neither state gates the run.
