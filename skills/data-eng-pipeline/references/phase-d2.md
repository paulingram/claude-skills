# Phase D2–D6 — Implement, review, and verify (Phases 2–6 verbatim)

Phases **D2 through D6 are the main pipeline's Phases 2–6 run verbatim** — the parallel team spawn (Phase 2), the Phase 3 paired review gate, Phase 4 reconciliation, and Phase 5 cross-layer integration + Phase 6 verification. Nothing about the evidence stack is relaxed for a data-engineering slice:

- **Phase 2 — parallel implementation.** The Lead spawns backend / data teammates with non-overlapping file scope per `team-spawning-and-review-gates`. Transformations (dbt models, Airflow tasks, stream processors, warehouse DDL) are implemented against the design the exploration produced and D1 approved. Every spawn brief carries the confirmed project principles block (`python "${CLAUDE_PLUGIN_ROOT}/scripts/principles/cli.py" brief --workspace <ws>`, v4.0.0) exactly as `appearance_mode` is carried, names the tier of its Phase 3 gate (`review_tier: 2`), and — when `--full-data` was NOT passed and no principle forbids sampling — the transformation's sample plan (`## Sample-first iteration (v4.0.0)`; `references/sample-first.md`): the teammate iterates on the stratified sample and runs the full data last. With `--full-data` the brief references no sample plan and every data step runs in full.
- **Phase 3 — the paired review gate.** Every teammate writes the schema v7 review-gate evidence (the 17 required fields including `real_not_stubbed`, `tests`, `integration_testing_review`, `test_completeness_review`, `reuse_compliance`, and the 5 Verified Agent Output fields) to `.architect-team/reviews/<task-id>.json`; an independent `task-reviewer` writes the `independent_review` block and a paired adversarial reviewer writes `adversarial_review`. Only both-pass opens the gate. Same gate as the main pipeline — data work does not skip review-gate evidence. **Review tier 2** per `skills/team-spawning-and-review-gates/references/review-tiers.md`: the teammate's self-review is the producer, the paired reviewer is the ONE independent verdict, and only when the two disagree does the Lead dispatch a second independent `task-reviewer` whose verdict is final for that round; the brief names the tier and the `independent_review` block records it with the reviewer's model. Tests are SELECTED, not the whole suite (v4.0.0): `python "${CLAUDE_PLUGIN_ROOT}/scripts/test_index/cli.py" build --workspace <ws>` then `python "${CLAUDE_PLUGIN_ROOT}/scripts/test_index/cli.py" select --workspace <ws> --phase D3 --baseline $BASELINE_SHA --json`; the teammate runs exactly the selected set (pins and unknown-mapping tests included) and cites the record (`.architect-team/test-selection-<ts>.json`) in the evidence beside the test output — the whole suite runs ONCE, at D8 (`skills/common-pipeline-conventions/references/test-selection.md`). The optional `principles_review` field cites the verdict sidecar when the workspace has confirmed principles.
- **Phases 5–6 — integration + verification.** Integration tests run against the live dev API with real dev data per `dev-api-integration-testing` (real backend, no mocks); any analytics-API surface is exercised front-to-back. The Integration Agent runs the SELECTED integration tests — `python "${CLAUDE_PLUGIN_ROOT}/scripts/test_index/cli.py" select --workspace <ws> --phase D5 --baseline <run-base-sha> --json` over the run's whole change set — and cites the selection record in the Phase 5 evidence; the full suite is D8's.

**The data-specific acceptance bar (non-negotiable).** Every transformation ships **≥ 1 blocker-severity validation rule** (the Stage 6 mandate, now implemented and executed — a transformation with zero blocker rules fails the gate) AND its **lineage emission** (the record is end-to-end traceable, per the exploration's lineage plan and `data-lineage-mapping`). Aggregate and per-endpoint metrics are wired per the Stage 6 observability plan. These are verified in the Phase 3 evidence and re-confirmed at Phase 5–6, not asserted.

The D2→D6 loop is unbounded — it runs until the slice is green end-to-end, never aborting on an iteration count; a failing check escalates as a solution requirement that the normal fix loop acts on.

**Bauplan-armed implementation (gated on the D−1 Part C verdict; a no-op when unarmed).** D2–D6 remain Phases 2–6 verbatim and the acceptance bar above is unchanged. Inside them, per `common-pipeline-conventions` `## Augment-never-replace discipline (v3.63.0)`: scaffold the project and author models through `bauplan-data-pipeline` rather than hand-rolling a lakehouse layout — this is also the greenfield path, reachable on stated intent alone when no marker can yet exist; land every S3 / external ingestion through `bauplan-safe-ingestion`, so the write goes to a branch and publishes by merge rather than straight to `main`; and emit each transformation's mandatory blocker-severity rule as executable `expectations.py` through `bauplan-data-quality-checks`. That last one is a **how**, never a **whether** — the ≥ 1 blocker-severity rule per transformation is mandated with or without Bauplan, and a bauplan-generated rule is measured at the Phase 3 gate exactly like a hand-written one. Where a Bauplan write rule and a CT6 default collide on a lakehouse operation, the Bauplan rule governs and the conflict is appended as a `precedence_conflicts[]` entry to the dispatch record; every dispatch is recorded there too.
