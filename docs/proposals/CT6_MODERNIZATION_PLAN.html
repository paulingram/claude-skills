Proposal · CLAUDE TEAM SIX (plugin slug architect-team) · v3.67.0 baseline · measured 2026-11-08 · Part II added the same day

Keep the careful robot team. Shrink its backpack.

CT6 is a team of robot helpers that builds software very carefully. It got so careful that it now reads a 65,000-word rulebook before every chore. This plan keeps the carefulness and removes the weight, using what Claude Code and the Claude 5 models can do today. Part I is the modernization; Part II adds six requested capabilities: a referencing mandate, codified project principles, smarter deletion, test selection, sample-first data work, and private-URL publishing.

1. What CT6 is, like you're five

Like you're five

Imagine you ask a team of robots to build a treehouse. One robot is the Lead: it reads your wish, makes a plan, and hands out jobs. Builder robots build. Checker robots look at the builders' work and say "not done yet" if anything is fake or untested. Hall monitors stand in the doorway and physically block a builder from saying "I'm finished!" without showing their homework. And the whole team writes down what it learned so the next treehouse goes better.

In Claude Code terms: the Lead is the orchestrator running the architect-team-pipeline skill. Builders are the backend and frontend agents. Checkers are the paired adversarial-reviewer, the task-reviewer, and the ×3 convergence reviewers. Hall monitors are the 7 hook scripts (a Stop hook that refuses to end the turn while work is open, a PostToolUse hook that blocks "completed" without an evidence file, a PreToolUse gate on every tool call). Memory is MemPalace. Those four ideas are the spirit of the repo, and nothing below removes any of them.

2. How a run works today

Like you're five

The Lead wakes up its memory, sorts your wish into "bug" or "feature" or "data," draws a map of the whole house, writes a plan and checks it covers every wish, splits the work, sends builders off in pairs with a checker each, refuses to call anything done without proof, glues the pieces together, clicks through the real app like a user, and only then writes the report and saves the work. Every step has a hall monitor.

5. The proposal: eight changes

Like you're five

Fix the broken to-do list first. Then turn the giant rulebook into one page of real rules plus a shelf of books the robots pull down only when needed. Any rule that matters gets a hall monitor; any rule that doesn't gets deleted. Give each robot a short job card instead of the whole manual. Send three checkers only when the job is scary. Use the new toolbox instead of borrowed tools. And stop printing a new edition of the encyclopedia every two days.

CHANGE 1 · FLOOR

Make CT6 run on Claude 5 at all

Setup writes CLAUDE_CODE_ENABLE_TODO_TOOLS=1 into ~/.claude/settings.json env next to the Agent Teams flag; the SessionStart hook checks the session actually has TaskUpdate and prints a one-line warning with the fix when it does not; the completion lock treats "task tools absent" as a measured gap instead of silence. Drop TodoWrite from all 39 agent tool lists.

Spirit kept
Evidence before assertion. The gate must know when it is blind.
Impact
Restores the Phase 3 gate and the completion lock on local Claude 5 sessions.
Risk
Low. Additive; one test per surface.
CHANGE 2 · RULEBOOK

One constitution, a shelf of references

Split common-pipeline-conventions into a ~3K-token constitution (the ranked "Read this first" list that already exists, the 8 ETHOS principles, and a table of pointers) plus one references/*.md per discipline, loaded only by the phase that needs it. Every SKILL.md: ≤ 500 lines, and the first 5,000 tokens must carry everything a run cannot lose at compaction. Lane skills shrink to the phase sequence plus pointers.

Spirit kept
Nothing is deleted, it is moved behind a pointer; the house "heading + STOP pointer + one paragraph" shape already exists.
Impact
Lead start load ~141K → ~20K (estimate); rules survive compaction.
Risk
Medium. ~137 prose-pin tests need re-homing (change 8).
CHANGE 3 · RULES

Every rule is a hook, a principle, or gone

Walk the 328 MUST/NEVER sentences in skills. Each becomes (a) a line in the constitution pointing at the hook or Layer-3 tool that enforces it, (b) one of the 8 principles, or (c) deleted. A rule nobody checks is a wish, and CT6's own ETHOS says evidence beats assertion. The 24 Layer-3 tools and 7 hooks stay; their prose shadows go.

Spirit kept
The producer is never its own checker: enforcement stays in code, where it already lives.
Impact
Biggest single reduction in instruction bytes; higher compliance on the rules that remain.
Risk
Medium. Needs a ledger so each deletion cites its hook or its principle.
CHANGE 4 · AGENTS

A job card, not the manual

Replace the 5 compiled boilerplate blocks with one ct6-agent-core skill preloaded through the agent's skills: frontmatter. Each agent file becomes a ≤ 2K-token role brief: who you are, inputs, output schema, what you never touch. Use effort per role, memory: project for mappers and reviewers so maps improve across runs, omitClaudeMd for pure verifiers, and evaluate native isolation: worktree against the custom worktree lifecycle.

Spirit kept
Reuse before build; honest boundary stays in the core skill.
Impact
system-architect 21K → ~4K; researcher dispatch 124K → ≤ 15K (targets).
Risk
Low–medium. sync_agent_boilerplate.py is retired, not rewritten.
CHANGE 5 · TEAM

Three checkers only when it's scary

Make reviewer fan-out a tiered parameter: tier 3 (×3 independent + synthesis) for architecture approval, master review, and map convergence; tier 2 (producer + adversarial) for every Phase 3 task; tier 1 (one verifier, often a prompt hook) for mechanical checks. Assign models by role: Fable 5.1 for Lead, architect, adversarial reviewer; Opus 5.5 for builders; Sonnet 5.5 for mechanical verifiers; Haiku 5.5 for bug-classifier and test-prod-safety-classifier.

Spirit kept
Independent verdicts where independence buys something; the adversarial pair stays universal.
Impact
Fewer dispatches per run; classification at 1/100th the price.
Risk
Medium. The tier table is a user decision (§8).
CHANGE 6 · TOOLBOX

Native orchestration over borrowed loops

Ship workflows/ scripts for the converge loops (map review, integration synthesis, editability, interaction): parallel() the reviewers, read typed schema verdicts, loop until all ok. Retire the ralph-loop dependency (the Stop-hook completion lock already provides "do not stop until done"). Keep Agent Teams as the optional interactive mode; document subagents + workflows as the default so -p and cloud runs behave identically. Make superpowers and cartographer conditional with a native fallback skill each.

Spirit kept
Unbounded solving, now in code; Default to action.
Impact
One fewer hard dependency now, two more if you accept §8 decision A.
Risk
Medium–high: reverses the v3.9.0 "never degrade" rule; user decision.
CHANGE 7 · FRONTMATTER

Label every skill with who may press it

user-invocable: false on the ~45 internal procedure skills (gone from the / menu); disable-model-invocation: true on the 7 lane drivers (only the command starts a run, which is what the skill-invocation gate already demands); paths: on data-eng and Playwright skills; context: fork for heavy sub-procedures (SQL mining, map review) so their transcripts never land in the Lead; move the PreToolUse / Stop hook registrations into the lane skills' hooks: so they run during a CT6 run instead of in every session. Trim descriptions toward the 1,536-char cap.

Spirit kept
The skill-invocation discipline becomes a property of the file, not a paragraph.
Impact
≈21K always-loaded tokens → ~6K; hooks stop taxing non-CT6 sessions.
Risk
Low. Verify plugin-skill hooks fire as documented before removing them from hooks.json.
CHANGE 8 · HYGIENE

Measure the backpack, stop printing encyclopedias

Add scripts/measure/instruction_budget.py: tokens loaded per lane start and per agent dispatch, recorded under docs/measurements/ and gated by changelog_check.py exactly like the suite bracket. CHANGELOG keeps the last 10 releases, the rest already belongs in RELEASE_HISTORY. CODEBASE_MAP becomes generated. Tests split into behavior tests and one manifest-driven structural lint that replaces hand-written wording pins. Release per capability, not per fix.

Spirit kept
Recorded, not asserted. The same discipline the suite bracket already has, applied to instruction weight.
Impact
Regressions in weight become visible; release cost drops from ~27 files to a handful.
Risk
Low.

7. A referencing system: yes, with three conditions

Like you're five

Instead of handing every robot the whole encyclopedia, you hand it a one-page map that says "before you build, go read chapter 4; before you test, read chapter 9." The robot reads only the chapters for today's job. This is a good idea. It only works if the map is tiny, the chapters are real, and a hall monitor checks that the robot actually went and read the chapter.

Verdict

Yes. It is the same mechanism Claude Code itself uses: descriptions load at start, a skill body loads on invocation, supporting files load only when read. It is also what CT6 already decided to do in v3.47.1 (the "heading + STOP pointer + one paragraph" house shape) and in claude-md-efficiency, and then did not finish: the conventions skill has 53 sections but only two STOP pointers and five reference files, and the whole skills tree has five references/ files in total. The proposal in Part I (changes 2 and 4) is this referencing system; this section makes it a mandate and names the pieces that are missing.

Today in CT6

  • Pointer shape exists, mostly unused. common-pipeline-conventions has a ranked "Read this first" list of 10 rules (good) followed by 2,200 lines of inlined procedure (the thing pointers are meant to replace). Two sections use the > STOP. Before X, Read references/Y.md form; the other 51 inline their body.
  • CLAUDE.md is already pointer-style (60 lines) and scripts/claude_md/claude_md_efficiency.py can assess and generate pointer CLAUDE.md files, but the skill gates itself on MemPalace being installed, so most projects never get it.
  • No index files. There is no "before a build, read this index" surface. docs/CAPABILITY_INDEX.md catalogs skills for humans, not for a phase.
  • No read enforcement. The tool-call ledger at .architect-team/run-history/<run-id>-toolcalls.jsonl already records every tool call, and skill_invocation_audit.py already proves a Skill was invoked after it was requested. Nothing proves a mandated reference was Read before the phase that depends on it.

Proposed

  • Condition 1: the map is tiny. One INDEX.md per domain (build, test, data, review, release), each under 60 lines: a table of "situation → read this file → what you will know after." The constitution (change 2) is the only always-loaded text; it points at the indexes, the indexes point at the chapters. Never a pointer to a pointer to a pointer: depth is capped at constitution → index → chapter.
  • Condition 2: the chapters are real and resolvable. Every pointer names a file and a heading. scripts/compliance/instruction_compliance.py gains a check that every pointer resolves (file exists, heading exists) and that no chapter exceeds the 5,000-token re-attach budget. Dead pointers fail the suite the same way a bad count does today.
  • Condition 3: a hall monitor checks the reading. Each phase declares its required reads in its index (required_before: phase-2). A new Layer-3 tool verify-required-reads reads the tool-call ledger and reports a required-read-skipped gap when a phase started without its reads; the Stop audit carries it as a measured gap, never as a block on its own (the honest boundary: it proves the file was opened, not understood).
  • Pointers are written as mandates in the imperative the repo already uses: "Before spawning a team, Read skills/…/references/spawn-brief.md and execute it in full." Plain-text pointers, not @imports: the docs say imports do not reduce context cost, a pointer does.

How it changes the codebase

Mostly moves, not rewrites: conventions sections become references/*.md files; five INDEX.md files are new; instruction_compliance.py gains two checks; one new file in hooks/vao/ plus one Stop arm; claude-md-efficiency drops its MemPalace precondition and points at the indexes instead. The ~137 wording-pin tests move with the text (change 8's structural lint).

Negatives to be aware of

  • Following a pointer is probabilistic. An agent under pressure skips the read. That is why condition 3 exists, and why the rules that must never be skipped are enforced by hooks, not by pointers (change 3).
  • More tool calls per phase. Each phase start costs two or three Reads. On a 10-phase run that is 20 to 30 extra calls, at roughly 50 ms of hook time each. Cheap next to 120K tokens per dispatch, but not zero.
  • Index drift. An index that lags its chapters sends agents to the wrong place silently. The resolvability check catches a missing file, not a stale summary; documentation-currency has to own the indexes explicitly.
  • After compaction the Lead forgets what it read. That is acceptable by design (it re-reads on demand), but the constitution must say so, or the Lead will work from the summary.

8. Codified project principles

Like you're five

Every treehouse project gets a short list of house rules, written down where everyone can see it: "all boards are the same width," "reuse a ladder before you build a new one," "the toy box is for any toy, not a box shaped like one toy." When you give the robots a document about your project, they pull the rules out of it and show you the list. Every builder has to follow the list. When the robots show you choices, they say which choices break a rule and why. In auto mode they pick a choice that follows the rules, and only stop to ask if every choice breaks one.

Today in CT6

  • No per-project principles artifact exists. The closest things: reuse-first-design (the extend → compose → reuse → build-new ladder with a Reuse Decision Log in design.md, which already covers your "recreate the function instead of reusing it" example); phenotypes (cross-project blueprints); the appearance_mode binding (strict / propose / innovate) that is set at intake, persisted in intake-state.json, and carried in every teammate's spawn brief, which is the exact mechanism a principles binding needs; and deploy_config.py, the pattern for a human-authored, agent-immutable config file.
  • hooks/discipline_registry.py is not this. It tracks which CT6 disciplines have been applied to a codebase, not the project's own design rules. Its per-workspace JSON registry under .architect-team/ is a reusable shape, though.
  • Nothing abstracts principles from user documents. intake-and-mapping reads codebases.json and requirement folders; proposal-refiner grades prose. Neither extracts durable rules.
  • Nothing labels options against project rules. Proposal-first mode presents a package; the SR fallback presents options. Neither marks a violation.
  • Your data-model example (a generic anonymized model that an agent specializes with one too-specific column) has no guard today: the architect checks the contract shape, not its generality.

Proposed

  • The artifact. docs/PROJECT_PRINCIPLES.md in the target workspace (committed, human-readable, pointer-shaped: one line per principle plus a link to its source), with a machine twin .architect-team/principles.json: {id, statement, scope: architecture|data-model|naming|reuse|testing|ui, source: {file, quote} | user-stated, status: proposed|confirmed, added_by, added_at}.
  • The skill. project-principles with four verbs. extract: when a markdown, PDF, or spoken instruction is provided at intake (Claude Code's Read tool reads PDFs natively, so no new parser), produce candidate principles each with a verbatim source quote, and confirm them in one AskUserQuestion as a domain gate; nothing becomes confirmed silently. add: "codify this" at any time, in or out of a run. show: the new command /architect-team:principles prints the confirmed list with sources, the same way /architect-team:discipline-status prints the registry today. check: a Layer-3 tool verify-principles-respected that takes a design, contract, or diff and emits one verdict per principle: respected / violated (why, where) / not-applicable.
  • Where it binds. The Phase 1 architect brief, the Interface Contract Approval mode of system-architect, and every backend / frontend / integration spawn brief carry the principles exactly as appearance_mode is carried today. Phase 3 evidence schema gains a principles_review field citing the check's verdict path. Your example becomes principle "the shared data model stays generic: no entity-specific columns in shared schemas; specialize in a view or an extension table", and the architect's contract approval checks it.
  • Presenting options. Whenever options are shown (proposal-first, SR fallback, diagnostic hypotheses), each is tagged fits or violates P-07 (why). Rule for autonomous runs: choose a fitting option and continue; stop with escalation-pending.md only when every option violates. Precedence: the user's explicit instruction in this run > confirmed principles > CT6 defaults.

How it changes the codebase

New skill + command + Layer-3 tool (hooks/vao/principles.py); one new field in review_evidence_schema.py (v8); one line in each of the six lane commands' front door (intake) and in the Phase 1 / Phase 2 brief templates; reuse-first-design links its ladder as the default principle set; pretool_unilateral_override_guard.py treats PROJECT_PRINCIPLES.md as human-owned (agents may propose, never edit silently). The appearance_mode rollout touched six commands, six lane skills, and the schema; expect the same footprint, which is why Part I's constitution should land first.

Negatives to be aware of

  • The verdicts are judgments. A hook can prove every principle was considered and a verdict was written; it cannot prove the judgment is right. The honest boundary has to say so on the artifact.
  • Over-codification recreates the bloat. Fifty principles per project is the conventions skill again. Cap the confirmed list (a soft 15), rank it, and make "retire a principle" a verb too.
  • Principles can contradict the requirement. The precedence rule above resolves it, and the run must say which principle it set aside and on whose instruction.
  • Extraction from a long PDF is lossy. The quote-per-principle rule keeps it auditable; the user still has to read the proposed list once.
  • Auto mode will sometimes pick the "fitting" option that is worse. The tag on the final report ("chose B over A because A violated P-03") keeps that visible.

9. Smarter about deleting things

Like you're five

Throwing away a scrap of paper you doodled on is fine. Throwing away the only copy of your homework is not. Right now the robots are told "never throw anything away without asking," so they ask about scraps. Instead: if it is a scrap (a temp file), throw it away. If a saved copy exists in the drawer (git has it, unchanged), throw it away and say where the copy is. If it is the only copy, or you scribbled on it since the last save, put it in a trash bin instead, and ask only if it must truly be gone.

Today in CT6

  • Blanket bans, no classification. All 39 agents carry a "Forbidden git operations" block (stash, reset --hard, rebase, amend, checkout other branch, clean -f). hooks/shared_rule_constants.py holds the six regexes and review_evidence_schema.py asserts none were used. This protects shared git state inside a run, which is right, and says nothing about file deletion.
  • No hook looks at rm, rmdir, find -delete, git clean, or git checkout -- path. The PreToolUse guard covers Edit / Write / NotebookEdit on ground-truth files only.
  • Asking is governed by prose. The "process gates vs domain gates" section says a destructive irreversible action is a legitimate reason to ask, with no definition of irreversible. 72 AskUserQuestion mentions across the surfaces; none is derived from a recoverability check.

Proposed

  • Soft delete by default. Agents move files to .architect-team/trash/<run-id>/<original-path> instead of rm. The trash is pruned at Phase 8 / worktree cleanup once the run is merged. Most "may I delete" questions disappear because nothing is lost yet.
  • A recoverability classifier, as a PreToolUse(Bash) arm. For each deletion-shaped command it extracts the target paths and classifies each with git: temp (under .architect-team/ per-run dirs, /tmp, caches, build output, merged worktrees) → allow. Ignored by .gitignore → allow. Tracked and clean (in HEAD and git status --porcelain empty for the path) → allow, with additionalContext naming the restore command. Tracked with uncommitted changes → ask, naming how many lines would be lost. Untracked and not ignored → ask. Not in a git repo or unparsable command (pipes, variables, globs it cannot expand) → ask. The six shared-state git operations stay deny during an active run exactly as today. This uses the hook permissionDecision: allow | ask | deny with a reason, which is the mechanism the docs give for exactly this.
  • Replace the prose. The 39 copies of the forbidden-operations block become one constitution line ("deletion goes through the classifier; shared git state is never rewritten in a run") pointing at the hook.

How it changes the codebase

New hooks/deletion_guard.py (stdlib: shlex to tokenize, subprocess for git ls-files / git status --porcelain / git cat-file -e HEAD:path), registered as a PreToolUse(Bash) arm beside the skill gate; the six regexes move from shared_rule_constants.py into it; one new section in the constitution; the compiled "Forbidden git operations" block is removed from the agents by the same pass as change 4. A fixture test matrix (temp / ignored / clean / dirty / untracked / no-repo / unparsable) is the acceptance test.

Negatives to be aware of

  • Shell parsing is heuristic. rm -rf "$DIR", xargs rm, find … -exec rm, and Python one-liners calling shutil.rmtree are hard to classify. The rule is fail-safe: unparsable means ask, which will annoy occasionally.
  • "In git" is not "recoverable from the remote." A clean tracked file whose commit was never pushed is recoverable only locally. The classifier checks HEAD, and the reason text says "local HEAD" or "on origin" explicitly.
  • Non-interactive runs cannot answer an ask. In -p or cloud mode an ask is a denial. The soft-delete default is what keeps those runs moving; the agent falls back to trash instead of stopping.
  • Trash can grow. Pruning is tied to merge, so an abandoned run leaves trash on disk until the worktree cleanup sweep. Acceptable, but it should be reported in the final report.

10. Run the tests that matter, not all of them

Like you're five

If you fix one squeaky stair, you check the stairs. You don't re-inspect every window in the house. Right now the robots re-inspect the whole house after every tiny fix. Instead: keep a list of which test checks which part, look at what changed, run only the tests for those parts (plus any tests you said must always run), and inspect the whole house once at the end before it is handed over.

Today in CT6

  • Phase 3 (per teammate): unit, integration, and Playwright are each required (test-completeness-verifier), and the teammate must "capture full test-suite output." Nothing scopes the run to the slice.
  • Phase 5 (integration): the integration agent "runs the full integration test suite locally first, then against the development API with live dev data," and since v3.65.0 must enumerate suite-manifest.json and run the ENTIRE dev Playwright project. mini-review-sweep carries the same whole-suite rule. Full-stack, frontend-only, and backend-only changes all take the same path.
  • The selector ingredients already exist, unconnected. hooks/frontend_impact.py maps a change set to frontend impact (file extensions, plus changed endpoints consumed in ROUTE_MAP / INTEGRATION_MAP): a selector precedent. hooks/lineage_graph.py (the Code and Data Lineage Graph) gives every function a func:// identity, runtime-witness trust, and transitive freshness: the function map you describe. suite-manifest.json records per test the persona, kind, and covers_elements. coverage-mapping maps requirements → tests, but not tests → functions. test-prod-safety-classifier already separates what may run against prod.
  • No human "always run" pin exists. The only standing pins are the prod smoke suite and the prod default-deny.

Proposed

  • A test index. <workspace>/.architect-team/test-index.json: per test id → files, func:// nodes, endpoints, UI elements (from the intuition map), kind (unit / integration / e2e), layer, last duration, always_run, trust (static or runtime-witnessed). Built by scripts/test_index/ from the CDLG's static call graph, and upgraded to runtime-witnessed when a coverage-per-test run is available (pytest-cov contexts, c8, Playwright traces → endpoints hit). Same trust gate the CDLG already uses: a static mapping is a hypothesis, a witnessed one is evidence.
  • A selector. select: diff against BASELINE_SHA → changed func:// nodes → transitive dependents (CDLG) → tests, plus every always_run pin, plus every test whose mapping is unknown (unknown is not "no tests," the same lesson as the completion lock). The selection and its reasons are written as evidence (test-selection-<ts>.json) and cited in the Phase 3 / Phase 5 evidence files.
  • Human pins. .architect-team-deploy.json (already human-owned and agent-immutable) gains tests.always_run: [ids or globs] and tests.full_suite_at: ["phase-8"]. A project can say "always run the billing suite" or "always run everything," and no agent can lower it.
  • Three tiers. Phase 3: selected tests for the slice. Phase 5: selected integration against live dev plus flows the frontend-impact detector names plus pins. Phase 8 (before merge to main): the full suite once, and the prod smoke suite. "Full every time" becomes "full once per run," not never.

How it changes the codebase

New scripts/test_index/ (build, select, witness); one new field family in deploy_config.py; frontend_impact.py and lineage_graph.py gain callers but no new logic; the Phase 3 and Phase 5 text in architect-team-pipeline, dev-api-integration-testing, mini-review-sweep, and test-completeness-verifier changes from "full suite" to "selected per the index, full once at Phase 8"; test-run-monitor records which selection ran. The v3.65.0 "ENTIRE dev suite" rule is an explicit reversal and should be logged as such in the CHANGELOG.

Negatives to be aware of

  • A stale or wrong index skips a test that would have failed. Three mitigations, all needed: unknown-mapping tests always run; the CDLG's transitive freshness marks the index stale when its inputs change; the Phase 8 full run still exists.
  • Static call graphs miss dynamic code. Reflection, dependency injection, config-driven dispatch, and event buses hide edges. Runtime-witnessed mappings fix this, but they need one instrumented full run per codebase to bootstrap and periodic refresh.
  • Playwright flows map poorly to functions. They map to endpoints and UI elements instead, which is why the index carries both; coverage will be coarser on the frontend.
  • An agent might lean on the selector to avoid a slow test. The pins are human-owned and immutable, the selection is recorded with reasons, and the Phase 8 full run is not selectable. That is the same three-part answer the deploy mandate uses.
  • Bootstrapping cost. The first run on a codebase builds the index and runs everything once; the savings begin on the second change.

11. Sample first on big data

Like you're five

If you want to know whether a new recipe works, you bake one cupcake before you bake a thousand. When a robot changes how a big pile of data is processed, it should first grab a small, well-chosen handful of that data, including the weird pieces, try the change on the handful, check the result, and only then run the whole pile.

Today in CT6

  • Sampling exists for discovery, not for development. data-dictionary samples roughly the first 100 records per table to infer grain, keys, and types; warehouse-sql-mining reads sampled rows. Neither is used to iterate a change.
  • The data-eng lane builds like the main lane. data-eng-pipeline Phases D2–D6 are "Phases 2–6 verbatim": implement, review, integrate, with no data-scale step. D0 explores, D7 refreshes the catalog.
  • expensive-verification-debugging is the nearest discipline (when a verify cycle is expensive, audit the whole pathway and batch fixes). It never says "make the cycle cheap by shrinking the data."
  • verification-planning lists venues (local run / dev / replay / seeded fixture / production) but not a sampled run.

Proposed

  • A sample-first discipline in the data lanes, default on, opt out with --full-data or a project principle. Before implementing a change that targets a subset (a filter, a partition, an entity type, a date range): profile the subset's structure from the data dictionary (grain, keys, partitions, distributions); stratify on the dimension the change depends on and always include edge rows (nulls, boundaries, duplicates, and the exact rows named in a bug report); size the sample as the smallest N that covers every stratum, and record sample-plan.json (strata, N, seed, source query, where it was materialized); materialize into a sandbox the dictionary already knows how to reach (temp table, local parquet, or fixture) under the read-only connection discipline; iterate the change against the sample with a before/after diff per stratum (row counts, key checksums, aggregate deltas); scale only when the sample passes, and use the sample result as the expectation file for the full run.
  • Sample groups, not rows. When the logic is aggregate-level (windows, dedup across partitions, joins), the sample must keep whole groups so the semantics survive; the plan records which keys were kept whole.
  • Where it plugs in. Data-eng Phase D2 (before implementation), the bug-fix lane when the bug is a data defect (B1 replication on the sample, B6 replay on the sample then full), and verification-planning gains "stratified sample" as a venue that is usually the cheapest faithful one.

How it changes the codebase

New reference skills/data-eng-pipeline/references/sample-first.md plus a stdlib helper scripts/data_dictionary/sampling.py that emits the plan and the stratified query from a dictionary entry; one new venue row in verification-planning; one paragraph in the bug-fix lane's data-defect branch; expensive-verification-debugging gains a first line ("before batching fixes for an expensive cycle, ask whether the cycle can be made cheap by sampling"). No hook changes; the sample plan is recorded as evidence like any other artifact.

Negatives to be aware of

  • A sample can hide the bug. Including the reported rows and stratifying on the change's own predicate reduces this; the full run remains the gate, so the cost of a miss is time, not correctness.
  • Small data makes this overhead. When the dictionary shows a full run takes seconds, skip sampling. The threshold belongs in the plan, not in prose.
  • Data residency and PII. Materializing a sample to a laptop may violate policy. Default to a sandbox inside the warehouse; local files only when the project principles allow it, which ties back to your anonymized-model principle.
  • Sampling logic is itself code that can be wrong. Keep it deterministic (seeded) and record the query, so a reviewer can rerun it.

12. Publish to a private URL when the setting says so

Like you're five

The robots are good at making pretty pages to show their work. Right now the page lives on Claude's website, which is fine for you but not for a friend without a Claude login. New option: the same page, but put on a web address you own, with a secret word in the link. You decide at setup where that address lives: a cloud service, a door on your own computer, or an address you name.

Today in CT6

  • No page-building skill exists. The 46 skills that mention "artifact" mean run artifacts (JSON verdicts, reports). readme-styling is the only presentation skill, and it targets markdown.
  • The hosting plumbing is half there. services/triage/server.py and services/seeded_mempalace/server.py already wrap handlers onto the stdlib http.server; services/common/ has an Ed25519 handshake, service_config.py, and bg_runtime.py for background daemons. Designed, tested, not live-deployed (the Librarian is the only installable).
  • Config precedent is clear. .architect-team-notify.json and .architect-team-deploy.json are human-authored, gitignored, agent-immutable opt-ins with a committed example file; architect-team-setup asks-then-applies.

Proposed

  • Skill page-publishing. Carries the plugin's own page contract (one self-contained HTML file, color tokens that follow light and dark, inline SVG diagrams, responsive at phone width, libraries only from pinned CDN URLs, no data leaves the page) so the page is portable to any host; when running inside Claude Code the native artifact guidance is also available and the skill defers to it for design. Two publish modes: claude (default; the Artifact tool, unchanged) and private-url.
  • Config .architect-team-publish.json (human-owned, immutable to agents, example committed): {"mode": "claude" | "private-url", "adapter": "local-port" | "gcp-signed-url" | "gcp-cloud-run" | "nominated-host", "token_ttl_hours": 72, "bind": {"host", "port", "external_ip"}, "gcp": {"project", "bucket" | "service"}, "nominated_host": {"ssh", "web_root", "public_base_url"}}.
  • Setup asks once. architect-team-setup detects the ecosystem (is gcloud on PATH and logged in? does the box have a public IP? is an SSH host configured?) and asks one question: where should shareable pages live? Options: a GCP URL (signed GCS object, or a tiny Cloud Run service checking the token), a port on this machine using its external IP, or a host you nominate. Nothing is opened or deployed until that answer is recorded.
  • Engine scripts/publish/publish.py. Writes the page, mints a token with secrets.token_urlsafe, and hands it to the adapter. local-port: a stdlib server (reusing the services/common runtime) that serves /p/<token>/<page>, denies everything else, expires tokens, and logs access; TLS when a certificate path is configured, plain HTTP on a LAN with a printed warning otherwise. gcp-signed-url: upload via gcloud storage and return a time-limited signed URL (no server to run). gcp-cloud-run: the same stdlib server in a container behind Cloud Run's HTTPS. nominated-host: copy over SSH into a web root the user's own server already serves. GCP and SSH adapters are conditional dependencies in the CONDITIONAL_PLUGINS sense: reported if missing, never gating.
  • Commands. /architect-team:publish <file>, /architect-team:publish --revoke <token>, /architect-team:publish --list.

How it changes the codebase

New skill, command, and scripts/publish/ with four adapters; services/common/bg_runtime.py gets its first live consumer; setup.py gains one question and one config writer; pretool_unilateral_override_guard.py adds the publish config to its immutable set; setup.py's conditional tier lists gcloud and ssh as optional tools. Stdlib-only holds for the engine and the local adapter.

Negatives to be aware of

  • CT6 becomes the operator of a public endpoint. A token in a URL leaks through browser history, chat logs, and referrers; a port on a dev box is an attack surface; a Cloud Run service costs money and needs IAM. Default TTL, revoke command, and access log are the minimum; the setup question must say this out loud.
  • No TLS from the stdlib alone. ssl is in the stdlib but minting a certificate is not; the local adapter is HTTP unless the user supplies a cert. The GCP adapters get HTTPS for free, which is a reason to recommend them.
  • You lose the Claude-native features. Comments routed to Claude, the shared database capability, the organization share list, and automatic theme detection by the host do not exist on a private URL. The page contract keeps the page self-sufficient, but the honest boundary should be printed with the link.
  • "The same talents" are partly Anthropic's. The native artifact-design guidance belongs to the Claude Code session, not the plugin. The plugin ships its own page contract (as readme-styling does for markdown) and benefits from the native skill when it is present.
  • A daemon outlives the session. The local server must survive the Claude Code process and be stoppable; bg_runtime.py was designed for this but has never run in anger.

Decisions only you can make

  • A. superpowers and cartographer: hard or conditional? The repo's v3.9.0 rule says abort rather than degrade. The proposal is to keep them as the preferred path but ship a native fallback skill for brainstorming / TDD / debugging / mapping so a run never aborts on a missing plugin. This reverses a rule you wrote on purpose.
  • B. The reviewer tier table. Which gates keep ×3? Proposed: architecture approval, master review, map convergence. Everything else gets producer + adversary.
  • C. Models by role. Proposed: Fable 5.1 for Lead, architect, adversary; Opus 5.5 builders; Sonnet 5.5 verifiers; Haiku 5.5 classifiers. The current uniform / split lever in set_default_model.py would gain a "by role" mode.
  • D. Release cadence. Per capability instead of per fix, with the CHANGELOG rotated to the last 10 entries.
  • E. Reversing "run the ENTIRE dev suite" (v3.65.0). The selector moves the full run to once per run before merge. You wrote the whole-suite rule after a real gap; this proposal argues the index plus pins plus one full run closes the same gap cheaper, but it is your rule to reverse.
  • F. Default host for private pages. GCP signed URLs (HTTPS, no server to run, small cost), a port on the box (free, HTTP unless you supply a cert), or a nominated host. The recommendation is GCP signed URLs where gcloud exists.
  • G. The principles cap. A soft limit of 15 confirmed principles per project, with retirement as a verb, so the principles file does not become the next 65K-token rulebook.
