**Run:** deng-comparison-20260802 · **Author:** system-architect · **Status:** analysis-only, no code changes proposed for immediate execution
**Citation convention:** deng-toolkit paths are relative to the read-only clone at `.architect-team/reference/deng-toolkit/`; CT6 paths are relative to this repo's root. All line numbers were verified against the files as read on 2026-08-02.
**Baselines compared:** deng-toolkit v1.0.0 (`.claude-plugin/plugin.json:3`, 16 commits, 2026-01-22 → 2026-01-29, one author under two git identities) vs CT6 v3.48.1 (`.claude-plugin/plugin.json:4`; 50 skills / 39 agents / 23 commands / 7 hooks / 21 Layer-3 tools; suite 6690 passing + 6 skipped across 223 test files, `CHANGELOG.md:20`).

## 1. Executive summary

deng-toolkit and CT6 solve the data-engineering knowledge problem from opposite ends. **deng-toolkit is catalog-centric**: it builds a *standing, warm, team-shared* metadata store — a Parquet catalog of every table/column/key scanned from SQL Server (`scripts/catalog_refresh.py:231`), an annotation layer, a JSON-LD ontology, and mined SQL patterns — and makes that store *interactively queryable* through a live MCP server (`servers/catalog_mcp/server.py:187-271`) so that any future conversation starts warm. It delivers intelligence, not code: nothing in it implements, tests, or ships a pipeline. **CT6 is pipeline-centric**: data knowledge is *derived per run, verified, and consumed by a delivery machine* — a 7-stage exploration flow with mandatory security and validation/lineage/observability stages (`skills/data-engineering-exploration/SKILL.md:200-331`), a corroborated data dictionary (`scripts/data_dictionary/data_dictionary.py:231`), a witness-gated lineage graph (`hooks/lineage_graph.py:470`), and a hook-enforced evidence stack that makes unverified claims structurally non-closable (`hooks/review-gate-task.py:396,413`, `hooks/review_evidence_schema.py:48-152`). deng's knowledge is warm but unverified and SQL-Server-bound; CT6's knowledge is verified and stack-agnostic but cold — re-derived per run and consumed by re-reading markdown. The highest-leverage move for CT6 is to adopt deng's *interface* (a standing, queryable, status-aware knowledge layer) while keeping CT6's *semantics* (freshness-gated, corroborated, fail-closed) — built on the engines CT6 already ships.

## 3. Where deng-toolkit is better (for data-engineering tasks)

Ranked by leverage. Each entry names the mechanism, the evidence, and what CT6 pays for lacking it.

### 3.1 A standing, warm, cross-project catalog — knowledge outlives the run
**Mechanism:** the catalog lives outside any project (`~/data-catalog`, `scripts/config.py:34`), is its own git repo pushed/pulled across the team (`scripts/catalog_sync.sh:121-175`; `README.md:114-127`), and every skill's first move is *check the catalog, not the database* — the scaffolded explorer agent is explicitly forbidden to scan databases while the catalog is fresh (`skills/deng-new/SKILL.md:323-330`).
**Why it matters:** DB metadata is expensive to acquire (live scans, credentialed connections, minutes of wall time) and changes slowly. deng pays that cost once per week per team; every conversation thereafter starts warm, and a teammate who has never connected to the warehouse inherits the whole map with `git pull`.
**What CT6 pays:** CT6's data dictionary is committed to the *target repo's* `docs/` (team-shared within that repo, `skills/data-dictionary/SKILL.md:26-27`) but is scoped per-codebase and rebuilt when stale (`skills/data-dictionary/SKILL.md:36-42`); nothing aggregates data knowledge across projects that consume the same warehouse, and there is no first-check-the-shared-catalog discipline. Two CT6 projects touching the same database each re-derive — and can diverge.

### 3.2 Interactive structured queryability — ask the catalog, don't grep the markdown
**Mechanism:** four catalog query tools + two annotation tools are callable mid-conversation (`servers/catalog_mcp/server.py:190-271`), returning ranked JSON (`server.py:29-98`), exact table detail (`:101-126`), and FK join paths in both directions (`:129-154`). The CLI mirrors it for scripts (`scripts/catalog_query.py:277-321`).
**Why it matters:** an agent mid-task asks "which tables mention churn and how do I join them" and gets a ranked, structured answer in one tool call — no file reads, no regex over a 1,500-line map, no context burned on prose.
**What CT6 pays:** every consultation of CT6's maps is a Read/Grep over markdown plus LLM parsing of prose — token-expensive, imprecise for structured questions ("what references `OrderItem.StatusCode`"), and unavailable to non-CT6 consumers. The machine sidecars (`data-dictionary.json`, `lineage-graph.json`) exist but have no query surface.
**Caveat (verified):** deng's *pattern* is right but this implementation's server entry point appears never to have run end-to-end — see §7; the 13 tests exercise the tool functions directly (`servers/catalog_mcp/test_catalog_tools.py:11`), not the stdio server.

### 3.3 Stored-procedure / SQL-pattern mining — reverse-engineering intelligence CT6 does not have
**Mechanism:** every programmable object's T-SQL definition is extracted (`analyze_procedures.py:116-143`) and parsed with sqlglot into join patterns, aggregations, filter idioms, and candidate metric formulas — ratios via `exp.Div`, metric-shaped `CASE`-with-aggregate expressions (`procedure_parser.py:387-457`) — then aggregated into global most-joined / most-filtered / discovered-metrics tables (`analyze_procedures.py:431-489`) and written back into the ontology as per-table `usageStats` (`:688-725`).
**Why it matters:** in a brownfield warehouse, the *real* business logic — how churn is actually computed, which join is canonical, which status codes mean cancelled — lives in decades of stored procedures, not in any document. Mining recovers it mechanically.
**What CT6 pays:** CT6's existing-code intelligence is application-code-shaped — functions, endpoints, data assets (`hooks/lineage_graph.py:69`) — and its data dictionary infers field meaning from names and sampled values (`data_dictionary.py:179`). Nothing in CT6 parses warehouse SQL objects, so a CT6 run against an old warehouse starts its Stage 1/2 modeling from documents and schema alone, blind to the embedded transformation logic deng would surface.

### 3.4 Usage-grounded importance — evidence of what the business actually runs
**Mechanism:** execution counts and recency from `dm_exec_procedure_stats`, Query Store, and SSRS report logs (`analyze_procedures.py:145-232`) rank every object (`:290-316`); the Excel review and the ontology enrichment both sort by this score (`generate_review_excel.py:105`), and unused objects surface as deprecation candidates (`skills/deng-analyze-procedures/SKILL.md:63-68`).
**Why it matters:** "most-executed" is ground truth about business importance that no amount of static analysis provides. It prioritizes documentation, review, and optimization where the traffic is.
**What CT6 pays:** CT6's Stage 4 volume/velocity analysis is estimate-shaped (`skills/data-engineering-exploration/SKILL.md:164-198` — projections and envelopes, not measurements), and nothing in the data dictionary records how *often* a table is read. CT6 prioritizes by requirement; it cannot currently prioritize by observed usage.

### 3.5 A durable, mergeable human-annotation layer on data objects
**Mechanism:** per-user JSON files under `<catalog>/annotations/<username>.json` (`annotations.py:53-55`) — so concurrent team edits never merge-conflict — merged and de-duplicated at query time (`:83-123`), with typed annotations (quality flags, deprecations) validated on write (`:140-162`) and written atomically (`:58-70`). Well-tested (30 tests, including path-traversal sanitization, `test_annotations.py:33-36`).
**Why it matters:** tribal knowledge ("this table is stale, use X instead") gets a *home attached to the data object*, survives forever, and is queryable by the same interface as the schema itself.
**What CT6 pays:** CT6 captures expert input in-run — domain-gate answers, bulk-verify resolutions — and persists prose into MemPalace (`skills/mempalace-integration/SKILL.md:117-121`), but there is no structured, per-object, queryable annotation record. A fact confirmed in run N is recalled as prose in run N+3, not looked up as a field on the table it describes.

### 3.6 A stakeholder review channel in the stakeholder's own tool
**Mechanism:** the review workbook meets business users in Excel — instructions sheet, yellow editable columns, dropdown validation, importance-sorted rows (`generate_review_excel.py:449-611`) — and `apply_review_feedback.py` ingests the returned file, archives the feedback as JSON (`:130-146`), and applies corrected names/meanings into the ontology (`:149-200`) with `--dry-run` support (`:351-355`).
**Why it matters:** the people who know what `StatusCode = 'CNCL'` means are rarely Claude Code users. An asynchronous, offline, zero-tooling review loop reaches them.
**What CT6 pays:** CT6's human checkpoints all assume the human is *in the session*. The delivery manifest (`CHANGELOG.md:68-78`) is outbound-only. There is no offline round-trip artifact for domain experts.
**Caveat (verified):** the round-trip is column-drifted as written on two of three feedback sheets — see §7 — which is itself instructive about un-reviewed producer/consumer pairs.

### 3.7 Explicit reproducibility snapshots
**Mechanism:** `catalog_snapshot.py` copies the catalog into a project's `artifacts/catalog/snapshot_YYYYMMDD/` with a `latest` symlink and a human summary (`catalog_snapshot.py:200-250`), so an analysis pins the exact catalog version it used.
**Why it matters:** "which schema did this model assume" is answerable months later.
**What CT6 pays:** CT6 fingerprints *specs* mid-run (`CHANGELOG.md:59`) and stamps maps with derivation times, but keeps no versioned snapshot of the data-knowledge state a given run consumed beyond git history of the docs.

## 4. Where CT6 is better

### 4.1 The verification and evidence discipline — deng's absence of it is visible in its own code
**Mechanism:** CT6 completion is *physically gated*: a task cannot be marked complete without a schema-v7 evidence file carrying 17 required fields plus an independent reviewer's verdict (`hooks/review_evidence_schema.py:48-152`; `hooks/review-gate-task.py:28,396,413`); 21 deterministic verifiers attack specific failure modes (`CHANGELOG.md:57`); Stop-hook arms make declared-but-unsatisfied gates and stale-spec dispatches non-closable (`CHANGELOG.md:59`); v3.48.1's whole existence is a FAIL-verdict review of a foreign release, closed fix-forward with fail-closed ledger reads (`CHANGELOG.md:5-20`).
**The contrast, concretely:** deng's review process found 6 issues once and fixed 1; the 5 open findings sit as markdown with nothing enforcing them (`todos/002-006`). And this analysis found, by reading alone, three defects that CT6's gates are specifically built to catch: an MCP entry point that cannot start as written (§7.1 — no test exercises `main()`; CT6's `verify-check-can-fail` exists precisely to refuse checks that never ran), an Excel produce/consume pair whose column indexes drifted apart (§7.2 — no round-trip test; CT6's paired-reviewer + red-first disciplines target exactly this), and a README config example whose key the code does not read (§7.3 — CT6's instruction-compliance lint machine-checks doc/code cross-references, `docs/INSTRUCTION_COMPLIANCE_RUBRIC.md` per `CLAUDE.md`). deng demonstrates what the absence of enforcement leaves behind *even in a small, competently written codebase*.

### 4.2 End-to-end delivery — intelligence is the first third of the job
deng ends where the work starts: it can tell you where churn data lives, but the pipeline that computes churn still has to be designed, built, validated, tested, and shipped by something else. CT6 takes the same ask through exploration → OpenSpec (`skills/data-engineering-exploration/SKILL.md:333-348`) → parallel implementation with paired adversarial review → integration/Playwright verification → retirement/evidence/doc gates → auto-merge and a stakeholder-readable delivery manifest (`CHANGELOG.md:68-78`). For a data-engineering *task* (not just a data-engineering *question*), deng is a component; CT6 is the factory.

### 4.3 Governance by default — security and observability are stages, not afterthoughts
Every CT6 data-eng run passes a mandatory security stage — per-attribute PII/PHI/PCI classification, encryption, access-control pattern, retention, right-to-be-forgotten (`skills/data-engineering-exploration/SKILL.md:200-228`) — and a mandatory validation/lineage/observability stage in which **every transformation must carry ≥ 1 blocker-severity validation rule** and per-endpoint metrics, checked by a 6-item convergence gate (`:230-331`, blocker rule at `:261`). deng's catalog carries no sensitivity concept at all — no PII field exists in the schema (`scripts/adapters/sqlserver.py:258-274`), and its `.env`-based credential handling even searches a hardcoded personal OneDrive path (`catalog_refresh.py:43-45`). A pipeline built from deng's intelligence inherits governance from nowhere; one built through CT6 cannot skip it (unilateral-override discipline, `skills/data-engineering-exploration/SKILL.md:378`).

### 4.4 Freshness correctness — invalidate on what changed, not on how long it's been
deng's staleness is one global 7-day wall clock (`server.py:177`; `catalog_query.py:335,361`) — hardcoded (the `cache_ttl_days` knob is dead config, `templates/targets.toml.example:35`), all-or-nothing, and blind to *what* changed. CT6's freshness is change-driven and node-scoped: content fingerprints (`hooks/lineage_graph.py:326`), per-node staleness when anything in the node's `calls`/`serves` subtree changed since `last_traced` (`skills/endpoint-trace-mapping/SKILL.md:145-147`; `hooks/lineage_graph.py:546,578`), an explicit `map_invalidated` override list (`skills/intake-and-mapping/SKILL.md:50`), and a witness gate that *refuses consumption* of a graph whose recall/hallucination is unproven (`hooks/lineage_graph.py:470`; `skills/endpoint-trace-mapping/SKILL.md:126-134`). A 6-day-old deng catalog reads as OK even if the schema changed yesterday; a 6-minute-old CT6 map is stale the moment its inputs change.

### 4.5 Breadth — engines, stacks, and platforms
deng is SQL Server end to end: pymssql (`catalog_refresh.py:81,97`), `sys.*` catalog views (`sqlserver.py:22-156`), T-SQL parsing (`procedure_parser.py:150`), SSRS (`analyze_procedures.py:209-232`); its shell tooling is bash-only and its `.env` discovery is macOS-shaped (`catalog_refresh.py:43-45`). CT6's data-eng surface spans dbt/Airflow/Dagster/Snowflake/Databricks/Kafka/Flink/Spark and nine workload classifications (`skills/data-engineering-exploration/SKILL.md:30,128`), the dictionary engine ships a complete SQLite adapter with the other engines as same-shaped adapters (`data_dictionary.py:75,315`; `skills/data-dictionary/SKILL.md:79-83`), and the whole suite is green on Windows and POSIX (`CHANGELOG.md:20`).

### 4.6 Corroboration — human claims are verified, not transcribed
This is the sharpest philosophical difference in the human channel. deng ingests human input *as truth*: annotations are stored as stated (`annotations.py:126-188`), and Excel feedback is written into the ontology with no check against the data (`apply_review_feedback.py:149-200`). CT6 verifies the human: every provided definition is corroborated against sampled reality — a claimed key is tested for uniqueness (`data_dictionary.py:210`), a claimed type is checked against actual value dtypes, and a conflicting claim is flagged ⚠ with confidence downgraded (`data_dictionary.py:231`; `skills/data-dictionary/SKILL.md:95-102`). The user who says "this table keys on customer_id" when it keys on a hash gets a dictionary that reflects the *real* field. deng would store the wrong claim forever.

### 4.7 Deterministic stdlib engines with pinned tests
CT6's data-eng machinery is stdlib-only, import-side-effect-free, and pinned by the suite (`scripts/data_dictionary/data_dictionary.py`, `hooks/lineage_graph.py`, `scripts/contract/interface_contract.py`; 6690 tests, `CHANGELOG.md:20`). deng requires uv + polars + pymssql + sqlglot + openpyxl + mcp (`servers/catalog_mcp/pyproject.toml:5-8`; `skills/deng-catalog-refresh/SKILL.md:56`) and tests 3 of its ~11 modules. The dependency wall matters operationally (pymssql wheels are notoriously platform-sensitive) and epistemically (an untested 800-line miner whose parser swallows exceptions broadly, e.g. `procedure_parser.py:219-220,285-286`, produces intelligence of unknown fidelity).

### 4.8 Provenance honesty as a first-class concept
CT6's dictionary stamps every field with a fixed provenance vocabulary — `direct-user-input` / `direct-code-comment` / `inference` / `live-data` (`data_dictionary.py:43`; `skills/data-dictionary/SKILL.md:92-94`) — and its no-DB path *states in the artifact* that live inspection did not run, forbidding `live-data` claims for unconnected databases (`skills/data-dictionary/SKILL.md:121-134`). deng's ontology does flag `auto_classified` vs `needs_review` (`build_ontology.py:509-520` — genuine credit, its reviewQueue is a good idea), but a regex-guessed semantic role and a human-confirmed one are otherwise indistinguishable downstream, and applied feedback merges silently into the same fields (`apply_review_feedback.py:177-191`).

## 5. Recommended CT6 modifications (ranked; analysis-only — suggestions, not a build plan)

Reuse-first throughout: every suggestion extends an engine CT6 already ships. Nothing here is authorized to build; each item is a candidate for a future run pending Paul's decision.

### R1 — A standing warm data-catalog service behind MCP query tools (highest leverage)
**The idea:** make CT6's *existing* data-dictionary artifact warm and queryable: a small installable service exposing `search_dictionary` / `get_table_details` / `find_relations` / `get_dictionary_status` over `docs/data-dictionary.json` (and, optionally, an aggregated home-dir index across repos), returning the same corroborated, provenance-stamped content the pipeline already produces.
**Reuse:** the dictionary engine's builder and relation maps are done (`data_dictionary.py:277,292,315`); the ranked-keyword search shape already exists twice in-house (`services/librarian/library_index.py:31-33` mirrors deng's weighting); the standing-service/installable pattern is the Librarian's (`scripts/setup/install_librarian.py`, `services/common/bg_runtime.py` per `CLAUDE.md`), and the live-serving-confirmation bar is the gateway's (`confirm_gateway_serving` pattern, `CLAUDE.md`).
**Effort / blast radius:** moderate; purely additive (a new `services/` member + installer command), zero pipeline changes required to ship v1.
**Honest tradeoff:** a live server is a new runtime surface that must meet CT6's own bar — end-to-end serving confirmation and tests that exercise the *entry point*, not just the functions (deng's §7.1 defect is the cautionary tale). And it must serve freshness with every answer (see R1's sibling rule in §6): a warm catalog that hides staleness would institutionalize exactly the wrong thing.

### R2 — A SQL-object mining skill (stored procedures / views + execution stats)
**The idea:** deng's most distinctive capability, rebuilt to CT6 standards: extract programmable objects and execution statistics from a target warehouse, parse out join/filter/metric patterns, and feed them into the data dictionary (as `inference`-provenance field/metric candidates, corroboration-gated) and the lineage graph (as `data_asset`-linked evidence).
**Reuse:** dictionary reference-map shapes (`data_dictionary.py:277`), lineage `data_asset` nodes (`hooks/lineage_graph.py:69,261`), the exploration Stage 2/3 consumption points (`skills/data-engineering-exploration/SKILL.md:72-160`).
**Effort / blast radius:** significant (a new engine + skill); additive. sqlglot is a third-party dep — either vendor a minimal stdlib pattern-extractor (house rule) or hold it behind an adapter boundary like tiktoken/litellm in setup (`CLAUDE.md`).
**Honest tradeoff:** mining is inherently best-effort (deng swallows parse errors wholesale); CT6's version must mark everything `inference`, surface parse-coverage stats, and never let mined "metrics" bypass corroboration — otherwise it imports deng's fidelity problem along with its idea.

### R3 — Persistent, structured annotation channel on data objects
**The idea:** adopt deng's per-user, merge-conflict-free annotation-file pattern (`annotations.py:53-55,83-123`) as the durable home for what CT6 already collects in-run — domain-gate answers, bulk-verify resolutions, quality knowledge — attached to tables/fields in the dictionary sidecar, mined into MemPalace, and (with R1) queryable.
**Reuse:** the dictionary sidecar as the anchor; `mempalace-integration` for recall; deng's type vocabulary (note / quality_flag / deprecation) is worth taking as-is.
**Effort / blast radius:** small; additive.
**Honest tradeoff:** CT6 should *improve* the pattern, not copy it — annotations carrying factual claims (keys, types) should route through `corroborate_definition` (`data_dictionary.py:231`) on ingest, so the store never accumulates confidently-wrong tribal knowledge the way deng's can.

### R4 — Usage-grounded importance in the data dictionary
**The idea:** when the live adapter's engine exposes usage/statistics views (SQL Server `dm_*`, Postgres `pg_stat_*`; SQLite has none), record per-table read/write recency and volume, and feed Stage 4's volume/velocity analysis with *measured* baselines instead of pure estimates (`skills/data-engineering-exploration/SKILL.md:164-198`).
**Reuse:** `build_from_sqlite`'s adapter shape (`data_dictionary.py:315`); deng's source list is the roadmap (`analyze_procedures.py:145-232`).
**Effort:** small-moderate per engine; additive. **Tradeoff:** engine-specific by nature; must degrade honestly (absent stats ≠ zero usage) — deng's own SSRS arm silently applies to only one hardcoded target name (`analyze_procedures.py:404`), the pattern to avoid.

### R5 — An offline stakeholder review round-trip for the data dictionary
**The idea:** a generate/apply pair (CSV via stdlib, or Excel behind an openpyxl adapter boundary) exposing dictionary fields with low confidence or ⚠ conflicts to non-Claude-using domain experts, applying returned corrections through the corroboration gate.
**Reuse:** the dictionary's confidence/conflict fields as the row filter; the helpdesk `logit` privacy engine (`CLAUDE.md`) for redaction before the file leaves the machine.
**Effort:** small-moderate; additive. **Tradeoff:** ranked below the annotation channel because CT6 already has strong in-session human gates; and the produce/consume pair MUST ship with a round-trip test — deng's column-drift bug (§7.2) is precisely the failure mode of an untested generate/apply pair.

### R6 — An optional JSON-LD emitter over the dictionary + lineage graph
**The idea:** a pure serializer from `data-dictionary.json` + `lineage-graph.json` into JSON-LD, for interoperability with the external catalog/lineage ecosystems Stage 6 already names (DataHub, OpenLineage — `skills/data-engineering-exploration/SKILL.md:267`).
**Reuse:** both sidecars are already machine-complete; deng's context/entity shapes (`build_ontology.py:378-398,446-553`) are a reasonable starting schema.
**Effort:** low (stdlib json); additive. **Honest tradeoff:** ranked last because CT6 has no internal consumer for RDF semantics — emit it only when a real external consumer exists. Formats without consumers rot into aspiration; deng's own sync docs advertise five YAML files that nothing generates (`skills/deng-catalog-sync/SKILL.md:59-67`; `catalog_sync.sh:195-201`).

## 6. Generalization — does the standing-catalog pattern apply to the full-stack pipeline?

deng's core pattern is: **a standing, warm, incrementally-refreshed knowledge layer + a formal semantic graph + a live query interface + a human annotation channel**, applied to database metadata. CT6 has an entire surface with the same shape — `CODEBASE_MAP`, `ROUTE_MAP`, `INTEGRATION_MAP`, `ENDPOINT_TRACE_MAP` + `lineage-graph.json`, `INTERACTION_INTUITION_MAP`, the data dictionary — all re-derived per run under freshness rules (`skills/intake-and-mapping/SKILL.md:48-51`). Does the pattern generalize?

**Where it clearly applies — the read side.** CT6's maps are already *persistent* (committed to the target repo) and already *incrementally refreshed* (skip-remap-if-current, `intake-and-mapping/SKILL.md:51`; transitive stale-node computation, `hooks/lineage_graph.py:546,578`). What they are not is *queryable*: every consumption is a file read plus prose parsing. A **codebase-intelligence MCP** — `search_map` (ranked keyword search across all map sidecars), `get_route_details` (a route's components/endpoints from `ROUTE_MAP`), `find_call_paths` (path queries over `lineage-graph.json` — the direct generalization of deng's `find_join_paths` from FK edges to `calls`/`serves`/`reads`/`writes` edges, `hooks/lineage_graph.py:72-87`), `get_map_status` (per-map `last_mapped`/`last_traced` + stale-node counts vs current git HEAD) — would make the whole surface warm and structured for a fraction of the token cost of re-reading markdown. Crucially, CT6 can do this *better than deng did*: deng's `get_catalog_status` answers from a wall clock (`server.py:157-182`); CT6's `get_map_status` can answer from `transitive_stale_nodes` against the actual changed paths (`hooks/lineage_graph.py:578`) — a staleness answer that is *true*, not just recent. The natural hosts already exist: the machine sidecars carry the content, and the Librarian service tier carries the standing-daemon + installer pattern (`services/librarian/`, `scripts/setup/install_librarian.py`).

**Where it does not apply — the correctness-sensitive write side.**
1. **Per-run gate inputs must stay per-run.** Phase −1's maps gate planning correctness; the freshness check exists so a run never plans against a stale map (`intake-and-mapping/SKILL.md:48-51`), and the witness gate exists so diagnosis never consumes an unproven graph (`endpoint-trace-mapping/SKILL.md:129-130`). A warm cache may *serve* the current-verified artifact; it must never *substitute* for the check. The rule: the server answers with the artifact + its staleness verdict, and pipeline consumption still runs the gate.
2. **The contract ledger must not become ambient.** The v3.48 retirement ledger is deliberately run-scoped debt with fail-closed reads and a non-closable gate (`scripts/contract/interface_contract.py:31-46`; `CHANGELOG.md:32`) — "warm" is exactly what a mock-serving ledger entry must never be. A standing ledger would blur run-scoped debt into background state, recreating the "mock that outlives its run" the discipline forbids.
3. **Convergence artifacts are verification events, not cache misses.** The value of the 3-reviewer map convergence and the interaction bulk-verify is the *act* of independent re-derivation; caching their outputs is fine (that's what the committed maps are), but the pattern must not tempt the pipeline to skip the act when inputs changed.
4. **Run state (`.architect-team/reviews/`, `teammates/`, evidence files) is ephemeral by design** — worktree-scoped (`CLAUDE.md` conventions) and meaningless across runs.

**The single highest-leverage generalization:** a **read-only, staleness-aware "map server" MCP over the existing machine sidecars** — R1's data-dictionary tools plus `find_call_paths`/`get_route_details`/`get_map_status` over `lineage-graph.json` and the map frontmatter, installable via the Librarian pattern, where **every response carries its freshness verdict** computed by the existing engines. It adopts deng's interface (warm, structured, one-tool-call answers, team-shared) while keeping CT6's semantics (change-driven staleness, witness-gated trust, evidence-backed content). The pipeline keeps deriving; the server serves what derivation produced and *says how fresh it is*. That one artifact would cut per-run context cost for every map-consulting agent, open CT6's intelligence to non-CT6 consumers, and change nothing about how correctness is established.

## 7. Honest boundaries

**What this analysis did NOT do.** No code from either system was executed: no deng scan against a real SQL Server, no MCP server launched, no Excel round-trip run, and no CT6 suite run within this analysis. Every claim is read-level, verified against source text with the cited lines. Runtime behavior — scan performance, parser fidelity on real T-SQL, LiteLLM/MCP interop — is unverified. The deng clone's last commit is 2026-01-29; upstream may have moved since.

**Read-level defect findings in deng-toolkit (stated "as written," not as observed failures):**
1. **MCP server entry point.** `main()` calls `asyncio.run(stdio_server(app))` (`servers/catalog_mcp/server.py:298-300`). Under the pinned SDK (`mcp>=1.2.0`, `pyproject.toml:6`; resolved 1.26.0, `uv.lock:322-323`), `stdio_server` is an async context manager yielding streams — not a coroutine `asyncio.run` accepts, and not a function taking a `Server`. Additionally, `.mcp.json:5` launches `python -m server` (top-level module), under which the relative import inside `call_tool` (`from .annotations import …`, `server.py:277`) cannot resolve. No test exercises `main()`, `list_tools`, or `call_tool` (`test_catalog_tools.py` imports the tool functions directly, `:11`). Conclusion drawn: the *functions* are verified; the *server* appears never to have been run end-to-end. I did not execute it; a differing runtime environment could in principle behave differently, but the code as written contradicts the pinned SDK's interface.
2. **Excel round-trip column drift.** The joins sheet writes 9 columns with "Is Correct?" at H (index 7) and "Notes" at I (index 8) (`generate_review_excel.py:553-563,591-599`), but the reader consumes `row[6]`/`row[7]` — the auto-generated "Business Interpretation" and the "Is Correct?" cell respectively (`apply_review_feedback.py:77-78`). The filters sheet writes the user's input in "Your Correction" at G (index 6) (`generate_review_excel.py:665-673`), but the reader consumes `row[5]` — the tool's own auto-generated interpretation (`apply_review_feedback.py:112`). Only the metrics sheet's indexes align (`generate_review_excel.py:494-504`; `apply_review_feedback.py:53-66`). As written, join verdicts land in the wrong field and filter "feedback" re-ingests the tool's own guesses. No round-trip test exists to catch it.
3. **README config-key mismatch.** The README's target example uses `databases = [...]` (`README.md:73`); the code reads `include_databases` with a default of scan-everything (`catalog_refresh.py:121`; `analyze_procedures.py:338`). A user following the README scans every accessible database silently. The shipped template uses the correct key (`targets.toml.example:14`).
4. **Assorted drift, cited where relied upon:** dual default catalog paths in one process (`config.py:34` vs `annotations.py:18`; also `hooks/scripts/ontology-updated.sh:5` vs `hooks/scripts/catalog-updated.sh:12`); README says 4 MCP tools vs 6 registered (`README.md:28-35` vs `server.py:190-271`); advertised YAML catalog files nothing generates (`skills/deng-catalog-sync/SKILL.md:59-67`); dead `[settings]` config block (`targets.toml.example:27-41`); hardcoded personal/employer strings (`catalog_refresh.py:43-45`; `generate_review_excel.py:480`; `build_ontology.py:270-271`; `analyze_procedures.py:500-502`).

**Fairness to deng-toolkit.** It is not zero-discipline: the MCP tools and config were built TDD with passing tests (`docs/plans/2026-01-27-feat-tdd-mcp-server-implementation-plan.md`; 50 pytest tests + a shell acceptance suite), it ran one multi-agent review pass and recorded findings honestly (`todos/001-006`), and its annotation module is genuinely well-engineered (atomic writes, sanitization, 30 tests). It is an 8-day-old, one-author, employer-specific tool that shipped real ideas fast. The defects above are what *partial* discipline leaves; they caveat adopting its implementation, not its architecture.

**Scope of the recommendations.** Every item in §5 and §6 is a suggestion with effort and tradeoff estimates that are engineering judgment, not measurements. Nothing has been built, scheduled, or specced. All of it is pending Paul's decision.
