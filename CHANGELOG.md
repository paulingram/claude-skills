## [4.1.5] — 2026-11-09 — deletion-guard-branches (PATCH: creating a branch restores nothing, and a variable chain is resolvable)

Field report, the third from the same lane: `S=/tmp/…/scratchpad; G=$S/lanes/a; …; W=$S/lanes/b; git -C $W checkout -b architect-team/followup 78d50816… ; cat >> $S/lead-checks/worklist.md <<'EOF' … EOF` asked — `CT6 deletion guard [ASK]: 78d50816…: unparsable -- relative path with no known working directory`. Two causes. The guard read every `git checkout` as a working-tree restore and took the start-point sha for a path. And the v4.1.4 variable rule marked `W=$S/lanes/b` unknown because its value carried a variable, although `S` had been assigned one segment earlier.

**Two refinements in `hooks/deletion_guard.py`.** (1) `git checkout` with `-b`, `-B`, `--orphan` or `--detach` creates or moves a branch and restores no path; the restore logic returns nothing for it (the teammate git discipline's shared-state arm still asks before a branch SWITCH, `git checkout <other-branch>`, as it did). (2) `_record_assignments` expands a value through the names already known before storing it, so a chain resolves; a value that STILL carries `$` or a backtick after that stays unknown. The deletion-discipline chapter's `unparsable` row states both. NEW tests (8) in `tests/test_deletion_guard.py`: the reported shape verbatim against a real repository, the orphan / detach / switch forms, the branch-switch arm's reason (never "unparsable"), `git checkout -- <path>` and `git checkout HEAD <path>` still classified, and a chain resolving to an allow.

Counts unchanged: skills **60**, agents **39**, commands **30**, hook scripts **9** (10 events), Layer-3 tools **26**. Suite **8963 -> 8971 passing + 2 skipped, 0 failed** (278 test files; linux/py3.13 bracket recorded in docs/measurements/).

## [4.1.4] — 2026-11-09 — deletion-guard-variables (PATCH: a variable the command itself assigns is a known path, not an unknown one)

Field report, the second from the same lane: `W=/tmp/…/lanes/cleanup-code; git -C $W checkout -- libs/a.py libs/b.py …; git -C $W status --short` asked on every run — `CT6 deletion guard [ASK]: libs/a.py: unparsable -- relative path with no known working directory`. `git checkout -- <paths>` discards uncommitted edits, so the guard is right to classify it; but it resolved `-C $W` to nothing because the variable, assigned two characters earlier in the same command, was treated like any unexpanded `$VAR`.

**One refinement in `hooks/deletion_guard.py`.** `_record_assignments` remembers `NAME=value` assignments that lead a segment (a bare `W=/path` segment, or `FOO=bar cmd …`) when the value is a literal, and `_expand_known_vars` substitutes `$NAME` / `${NAME}` in every later token of the same command before the base and the targets are classified. A value that itself carries `$` or a backtick stays unknown, so `W=$HOME/x; rm -rf $W/build` still asks as unexpanded. With the base known, the reported command classifies for real: clean tracked files allow, a file with uncommitted edits asks with the reason that matters (`tracked-dirty`), which is the discipline working as written. The deletion-discipline chapter's `unparsable` row states the rule. NEW tests (3) in `tests/test_deletion_guard.py`: the reported shape clean and dirty against a real repo, the braced and prefix-assignment forms, and the unexpanded-value control.

Counts unchanged: skills **60**, agents **39**, commands **30**, hook scripts **9** (10 events), Layer-3 tools **26**. Suite **8960 -> 8963 passing + 2 skipped, 0 failed** (278 test files; linux/py3.13 bracket recorded in docs/measurements/).

## [4.1.3] — 2026-11-09 — deletion-guard-heredocs (PATCH: a commit message is data, not a command; the guard stops asking about apostrophes)

Field report: a `git add … && git commit -q -F - <<'EOF' … EOF` whose message contained "the engine's config" asked for confirmation on every run — `CT6 deletion guard [ASK]: … unparsable -- the command could not be tokenized (unbalanced quotes)`. The guard split the command on newlines, fed each heredoc line to the tokenizer as if it were a command, and applied its fail-safe ("an unparsable command may be deleting something, so ask") to a line that was prose.

**Two refinements in `hooks/deletion_guard.py`.** (1) `strip_heredocs` removes every here-document BODY before the command is segmented: the opener stays, the lines up to the terminator go, an unterminated heredoc drops the rest. A heredoc body is data fed to the command — a commit message, a file's content — never a command of its own. The `python - <<EOF` path is unaffected: its deletion check still reads the full text, so a `shutil.rmtree` inside a Python heredoc is still seen. (2) A segment that cannot be tokenized asks only when `_DELETION_SHAPED_RE` finds a deletion-shaped word in it (`rm`, `rmdir`, `unlink`, `shred`, `find`, `xargs`, the Windows verbs, `git rm|clean|checkout|restore|reset|branch|stash|worktree|push|…`, the Python deletion calls); any other unparsable segment deletes nothing the guard knows of and is silent. `rm -rf "half quoted` still asks; `echo 'it's fine` no longer does. The deletion-discipline chapter's `unparsable` row states both rules. NEW tests (6) in `tests/test_deletion_guard.py`, including the reported command verbatim, a heredoc body that mentions `rm -rf`, and the Python-heredoc control.

Counts unchanged: skills **60**, agents **39**, commands **30**, hook scripts **9** (10 events), Layer-3 tools **26**. Suite **8954 -> 8960 passing + 2 skipped, 0 failed** (278 test files; linux/py3.13 bracket recorded in docs/measurements/).
